# 中文导读 · uibc-core

> 这份文件只有一个目的：让第一次打开本仓的中文读者，在五分钟内知道**它是什么、它不承诺什么、它被篡改时到底拦不拦得住**。
> 全仓英文为主，本文是中文补充，不替代 README，也不改变任何对外口径。

---

## 一、一句话

uibc-core 是一个**智能体生命周期证据包**与**复核器**：它把"这个 agent 是谁、做了什么、凭什么被允许做"打成可被别人离线复算的包，并给出三值判定——`PASS` / `FAIL` / `INCONCLUSIVE`。

**`INCONCLUSIVE` 永远不能被洗成 `PASS`。** 这是本仓最硬的一条设计约束。

---

## 二、PASS 到底等于什么（原句照抄，不得改写）

> A uibc PASS means: within the observed evidence boundary, no violation was detected. It does not claim the agent was correct, safe, or wise; that the recorded inputs were true or complete; or that any real-world outcome followed.

中文：**在观测到的证据边界内，没有检出违规。** 它不宣称 agent 是正确的、安全的或明智的；不宣称记录的输入为真或完整；也不宣称现实世界里发生了什么结果。

这句话看着弱，但它是本仓能被外部信任的首要原因：**别人能核验的只有"有没有检出违规"，核验不了"它是不是个好东西"。**

---

## 三、三律在这份代码里分别落在哪

| 三律 | 本仓对应物 | 位置 |
|---|---|---|
| **有籍**（Registry） | manifest 里的 agent_id / owner / agent_type / version；登记事件写进生命周期链 | `uibc_core/` + `registry/` |
| **有证**（Evidence） | 证据条目的内容哈希 + `evidence_root` + Ed25519 封签（公钥随包走，可 pin） | `uibc_core/signing.py`、`verify.py` |
| **有门禁**（Gates） | **20 组检查**（逐项编号与覆盖见 `docs/EVIDENCE-INDEX.md`） + 组合校验（K1–K8）；任一不过即 FAIL 或 INCONCLUSIVE | `uibc_core/verify.py` |
| **触点即门** | 每一次"改状态/换钥/回滚"都必须被判一次，不存在"默认放行" | 同上 |

## 四、被篡改时到底拦不拦得住（2026-11-22 实跑）

复跑命令（不需要装依赖、不需要账号）：

```bash
python tools/mutation_benchmark.py
```

**本仓构造的 21 类单点篡改** × 三种验证模式（open / pinned / head-pinned），结果（2026-11-22 复跑，与 11-20 逐位一致）：

| 模式 | 含义 | 假接受率 | 未解释接受 |
|---|---|---|---|
| **open** | 陌生人只拿到包，公钥随包走，无预置信任 | **9.5%（2/21）** | **0/0/0** |
| **pinned** | 依赖方另持公钥，验证时 pin 住 | **4.8%（1/21）** | **0/0/0** |
| **head-pinned** | 专治"整包回滚"，需外部单调锚 | **0%（0/1）** | — |

**"未解释接受 = 0"的意思**：两处被 `PASS` 的篡改，都被检查项明确标为"低置信/需人工确认"，**没有一处是悄悄放过的**。

### 被放过的两类，性质完全不同

| 篡改 | open | pinned | 原因 | 怎么解 |
|---|---|---|---|---|
| **M17 换钥重签（keyswap）** | PASS | FAIL | open 模式公钥随包，密码学上无法区分"新钥"与"合法换钥" | 用 pinned，或与登记簿比对 |
| **M20 整包回滚（旧包冒充新包）** | PASS | PASS | 缺"单调性"——包本身自洽，看不出它比某个新包更旧 | 需外部锚（透明日志 / OTS）；**当前 OTS 仍 `PendingAttestation`，此格尚未覆盖** |

> 换句话说：**这 9.5% 不是漏洞清单，是定义域边界。** 我们主动把它写出来，因为它比"我们全都拦住了"更可信。

## 五、复核一次要多久（2026-11-20 实测，同一条命令两台机器）

命令只有一个：

```bash
python tools/latency_probe.py
```

| 机器 | 干净包 `base`（n=50） | 篡改包 `m_M12`（n=10） |
|---|---|---|
| Windows / Python 3.13（2026-11-19） | median **19.74 ms** · p95 **26.64 ms** · max **38.75 ms** | median 18.42 ms，判定 `FAIL` |
| Linux / Python 3.12（2026-11-20） | median **7.67 ms** · p95 **7.85 ms** · max **8.44 ms** | median 7.71 ms，判定 `FAIL` |
| Linux / Python 3.12（2026-11-21，公网干净克隆复跑） | median **7.78 ms** · p95 **8.69 ms** · max **10.02 ms** | median 7.72 ms，判定 `FAIL` |

**两点必须说清**：

1. **延迟是机器相关量，跨机不能横向比。** 上面三行是同一条命令在机器上的输出，不是产品规格；同一版本在不同硬件/系统上相差可达 3 倍（本仓两机即 7.78 ms 对 19.74 ms），**把两个数字并排比大小没有意义**。你机器上跑出来的那个数才算数——所以我们不写单一分位数当卖点，也不写"p99 33.6ms"这种只能复现一次的句子。
2. **单位是整包复核**（全部证据文件哈希 + 生命周期链校验 + Ed25519 验签 + 索引一致性），不是"单次调用判定"。**不要**拿它和策略引擎的亚毫秒指标直接对比——那不是同一个操作。

观察到一个反直觉现象：**篡改包比干净包更快**，因为第一处不一致就返回，不跑完全部检查。这不是性能优化，是逻辑决定的。

## 七、本仓现在还差什么（照实写）

1. **外部复核节点 = 0**：复核的独立性目前依赖同一作者的两份实现，这不是第三方复现的证据。
2. **OTS 外部锚 `PendingAttestation`**：所以 M20 那一格还不能宣称已覆盖。
3. **`gate()` 单次判定尚未单独基准化**：上面只有整包复核的分位数。
4. **版本真源曾出现双仓不一致**：本文件所属版本请以本仓 `CHANGELOG.md` 顶端为准。
5. **红队有一处灰区**：16 例攻击里 13 例被拒、**1 例灰区**、2 例按定义放行。灰区是 **RT05（删掉 `seal.json`）判定 `INCONCLUSIVE` 而不是 `FAIL`**——该拦未拦到底，属待收紧项；放行的两例是 **RT08（50MB 证据文件，41 ms 内通过）** 与 **RT10（攻击者自洽重签换钥）**，后者的公钥随包，密码学上无法与"合法换钥"区分，属定义域边界。我们只报 13/16 而不写这三例的性质，就是在藏缺口。
6. **"全量绿"是有前置条件的话**：全量套件需要 `.[verify,interop]`（`cryptography`）。裸 venv 里会成片失败（缺 `cryptography`），Windows 与 Linux 上跑出的用例数也不一样。"零依赖"（单文件 pyz 路径）与"全量绿"（装 extras 后跑测试）是两件事，不能合成一句；具体数字以仓内 `STATUS.md` 为准，我们不在导读里钉死。
7. **克隆命令曾指向不存在的分支**：旧版 README 与本文写 `--branch release/v1.1-precheck`，该分支**在本仓并不存在**，外人照着敲会直接失败。已改为 `main`，并用公网干净克隆实测跑通 `CONSISTENT`——这类错误的性质是"引用正确、命令错误"，比引用 404 更隐蔽。
