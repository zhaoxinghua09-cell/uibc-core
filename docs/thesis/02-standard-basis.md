# 2　相关工作与标准依据

本章的任务不是罗列文献，而是把本文用到的每一条外部依据落到原文位置，并说明本文与之的相同、相近与不同。凡本文未能取得原文者，一律不写入；凡本文与之存在差异者，逐条写明，不作含糊处理。这一处理方式直接决定了本文的可信度边界：读者可以按本章给出的条款位置逐条回查，若发现问题，纠正成本低于争辩成本。

依其作用，本文的外部依据分为三个层次：构件级（如何构造可验证的材料）、语义级（如何解释这些材料、给出何种结论）、实践级（实现在细节上必须避免哪些陷阱）。以下依次说明。

## 2.1　构件级依据：透明日志的树与证明

本文的位置判定来自透明日志。RFC 6962 定义了 Merkle 树的构造方式、包含证明（inclusion proof）与一致性证明（consistency proof）的交换格式，并引入树头（tree head）作为某一时刻集合状态的可签名摘要。RFC 9162 给出第二版，明确树规模（tree size）的表示与证明验证的边界条件。

本文取用其中两项。第一项是“树头 + 包含证明路径 + 树叶序号”这三样材料，在只持有树头的情况下即可确认某条叶子属于某个规模为 n 的集合。第二项是“树规模须显式携带”这一要求，它使“该记录出现时集合中有多少条”成为可核事实，而不是由记录自身声称。前一项回答“这条记录在当时存在”，后一项回答“当时整批有多大”。两问合并，才构成本文所说的位置证据。

本文未取用一致性证明，这一点须明确写出。一致性证明回答的是“此刻的树与先前观察到的树是否同源增长”。在单包离线场景下，判定者手里只有一份包与一个树头，没有第二份树头可比，一致性证明因此无从验证。本文的处理是不使用、不假装使用：把“此后未新增”明确列为包内不可判定的问题，交由外部观察解决。这一取舍由 2.4.1 节所述的草案条款支撑。

## 2.2　构件级依据：时间戳的时序锚定

RFC 3161 定义了时间戳权威（TSA）的请求与响应格式，其响应格式（第 2.4.2 节）规定时间戳令牌包含被签署的摘要、签发时刻与 TSA 签名。本文用其确定“该摘要于某时刻已存在”。

使用边界须一并写清：时间戳只提供时序，不提供内容真实性。TSA 签署的是摘要值，它不核对摘要对应的内容是否正确、是否完整、是否由某智能体产生。因此本文在判定表中把时间戳单独列为一类证据，其失败只影响时序结论，不影响内容与位置结论。同理，本文不把 TSA 视为判定者，判定由本地完成，TSA 的结论仅作为一项输入。

## 2.3　构件级依据：签名、规范化与编码

RFC 8032 规定 Ed25519 的密钥与签名表示。本文采用它的一个附带性质：签名过程不使用随机源，同一密钥对同一输入产生同一签名字节。该性质对本文有实际用处——两个实现在同一份包上计算出的签名可以直接逐字节比对，比对失败即说明二者对输入的理解不同，而不必再判断“是否使用了不同的随机数”。

RFC 8785 规定 JSON 的规范化序列化（JCS），消除键序、数字表示与空白差异带来的摘要分歧。本文的所有摘要计算均先经规范化，再取哈希；规范化规则本身写入包格式说明，使其成为可复核的公开约定而非实现内部约定。

RFC 4648 第 4 节规定 base64 编码。此处本文作了一项策略选择：严格解码，拒绝非规范填充与多余字符，而非宽容接受。理由不是个人偏好，而是 draft-maintainer-1f916 第 3.6 节明确指出的事实：宽容解码器对畸形输入的处理并不一致（有的静默截断，有的强制为零字节），两个实现对“非法字节”理解不同，就会对“哪份证明通过验证”得出相反结论。严格解码因此是消除分歧的必要条件，本文将其作为明文写出的策略，并在第 4 章对应为一项判定项。

## 2.4　语义级依据：智能体回执与记录类草案

### 2.4.1　链内完整性与它的能力上限

draft-noa-scitt-ai-agent-receipt 第 3 节给出回执结构，第 5 节给出哈希链与完整性要求：每份回执携带单调递增的 chain.seq（创世为 0）与 prevHash；验证者核验一段回执时须确认每个 prevHash 等于前一份回执的 chain.hash、创世回执的 prevHash 为空值，以及在存在已签署检查点时，检查点权威须绑定到创世密钥，从而拒绝由“重设链头”攻击者制造的外来检查点。

同一节紧接着给出该 profile 的能力上限，原文表述明确：本 profile 可检出呈现链内的带内篡改与尾部截断，但它本身不检出等同分叉（equivocation），即签发者对两条分叉链分别签名；检出等同分叉须依赖登记到 SCITT 透明服务或等效的外部见证。

这一条对本文有决定性意义。本文在第 5 章与第 6 章把“链尾收据不能仅由包内材料判定”列为局限，读者可能据此认为本文能力不足；而该草案表明，这一上限并非本文实现的缺陷，而是链式结构在单包条件下的固有边界，标准文本已明文承认。本文据此把该局限改写为一项结构性说明，并援引该节作为依据，而不是作为自我批评。

### 2.4.2　身份绑定的两级归因

同草案第 6 节区分了两个层次：agent.id 是签名者自述的标签；若要确认“是哪一个智能体在行动”而非仅仅“某个受信密钥签了名”，验证者需要一份把 agent.id 绑定到其授权 kid 的身份清单。清单存在时，(agent.id, sig.kid) 配对未获授权的回执或检查点必须作为不可信拒绝；清单不存在时，归因只到密钥级，且实现必须向依赖方明示这一限制。

本文据此把身份相关判定分为两级：密钥级（签名有效且密钥可对应）与主体级（另有清单支撑 id 与密钥的绑定）。两级均不足时，判定为不可判定而非通过，并在结论中写明归因止于密钥级。这一处理直接来自上述条款，本文不作改写。

### 2.4.3　锚定规则与四值裁决：本文与其关系的如实说明

draft-maintainer-1f916-agent-record 第 3.6 节给出两条本文必须正面回应的规定。

第一条是锚定规则（anchor rule）：每一次签名校验都需要一个公钥；若该公钥取自被测工件自身，则“签名通过”只证明该工件内部自洽——对手可以自行生成密钥对，用它签署一份伪造的档案及其检查点，再把两者一并交付，验证照样通过。只有至少一个密钥经由工件所不能控制的通道到达验证者（调用方提供的注册表密钥，或调用方钉定的见证密钥，且其连署覆盖同一 (log, tree_size, root)），该次验证才算 anchored。原文并以 MUST 规定：验证者必须接受调用方提供的注册表密钥与见证密钥，必须在每条签名记录上说明使用了哪把密钥，且对未锚定的运行不得给出高于 unanchored 的结论。

第二条是四值裁决，原文以 MUST 要求实现：witnessed（全部证明通过，且调用方钉定的独立见证连署覆盖该检查点，并声明其与此前观察到的链头连续）、consistent-unwitnessed（全部证明通过但无钉定见证连署，其结果依赖注册表声明的时间，不得报告为完全验证）、unanchored（全部证明通过，但所有密钥均来自被测工件，此结论只主张内部自洽，不主张真实性）、diverged（任一证明失败、密钥与调用方钉定不符、见证拒绝覆盖该链头，或已见证链头与注册表冲突）。

本文必须说明的是：本文采用三值裁决（未检出违规、检出违规、无法判定），与该草案的四值裁决并非同一维度。四值刻画的是“锚定程度 × 连续性状态”的组合，其结论仍以“证明是否全部通过”为前提；本文三值刻画的是“违规是否存在 × 是否可判”，并在设计上拒绝把“无法判定”折叠为“通过”。两者的对应关系见表 2-2。本文在此明确：三值裁决的思路受该草案四值裁决的启发，本文不主张首创；本文与之的差别在于分解维度不同，且本文把“不可判定”作为一等结论而非中间状态。

### 2.4.4　实践级依据：两条实现要求

同一节还给出两条实现层面的要求，本文直接采用，且因其属草案明文，在第 4 章的判定项分类中计入“草案明文规定”而非“本文自定”。

其一，实现须在使用前把树规模与叶序号校为非负整数并落在实现的精确整数范围内，且折半时使用整数除法而非位移。原文给出的失效场景是具体的：在使用把位移运算强制为 32 位整数的语言中，树规模 2^32+1 会使折半循环在“把前一树根绑定进新树”这一步之前终止，而最终检查仍然通过，从而以极低代价同时伪造包含证明与一致性证明。

其二，实现须在解码前把每个哈希校为恰好 64 位小写十六进制字符。理由即 2.3 节所述解码器分歧：对畸形输入，宽容解码器的行为并不一致。

这两条的共同指向是“输入校验先于计算”。本文把它们写成判定表中最前面的两项，并规定其失败立即终止后续判定——因为在其之后的所有结论都以这两项的成立为前提。

### 2.4.5　执行前记录取向的差异

draft-sharif-agent-audit-trail 给出审计记录的格式与流程，其第 3.1 节列强制字段、第 3.2 节列可选字段、第 3.3 节列字段约束，第 4 节给出执行前记录阶段（含第 4.2 节执行前要求与第 4.3 节高风险系统要求）。

本文与其取向存在实质差异，须写明：该草案把记录置于执行之前，使“将要做什么”在执行前即被固定并可事后比对；本文只做执行后判定，对包的构造发生在行为完成之后，因此本文不具备“执行前约束”的能力，也不能检出“行为与事前声明不符”这一类问题。本文不掩饰这一差异，并把它列入第 6 章的局限。

## 2.6　本章小结

本章把本文的外部依据分为三层。构件级依据（RFC 6962、9162、3161、8032、8785、4648）提供构造与验证的基本件，其条款本文直接采用，取用范围见 2.1 至 2.3 节。语义级依据（draft-noa、draft-1f916、draft-sharif）提供解释框架，本文从中取用锚定规则、身份两级归因与链内完整性要求，并在裁决维度上作出自己的分解。实践级依据（1f916 第 3.6 节的两条实现要求）被本文直接写入判定表最前面两项。

本章同时写明了三处差异与一处能力上限：不使用一致性证明、不采用执行前记录、三值裁决与四值裁决维度不同，以及链式结构在单包条件下不检出等同分叉。这四项是本文可信度的组成部分，而不是需要回避的短处——因为它们都可回查，且在原文中有明确位置。

最后须指出一条本章的依据不能支撑的结论：以上任何一条外部条款，都不能用来论证本文方法优于其他方法。条款界定的是应当如何构造与如何解释，不是优劣比较的依据。因此本文全篇不作此类表述，第 5 章的对照结果亦仅用于检验可证伪性，不作排名。
