The 11 failures, in two piles · 11 个失败，分两堆

Pile one — 8 findings about an external platform's resolver endpoint

  • Seven malformed or unresolvable DID inputs (non-DID string, wrong method, numeric type, 4096-char DID, injection characters, path traversal, nonexistent did:cn:agent) each returned HTTP 200 with success=True while the resolution itself FAILED. The truth is only in the resolutionStatus field — a caller that reads the success flag is silently misled. The bench names this pattern in its own notes: a contract trap.
  • One TLS baseline probe failed with an SSL version error (the regression above).

八个发现指向一个外部平台的解析端点：七种畸形或不可解析的 DID 输入，解析明明失败，端点仍回 200 并写 success=True，真话只在 resolutionStatus 字段里。只读 success 标志的调用方会被静默误导，台子在自己的注记里把这叫作契约陷阱。

Pile two — 3 findings about the resolver under test

  • Loopback not restricted: a did:web document pointing at a loopback address resolves successfully.
  • Downgrade followed: an HTTPS fetch answered with a 302 redirect to plain HTTP is followed; HTTPS constrains only the first hop.
  • No size cap: a 20 MB DID document is accepted and parsed (0.2 s, 65 MB peak memory) with no size limit applied.

三个发现指向被测解析器自身：回环地址未限制；https 被 302 降级到明文 http 时照样跟随；20MB 文档照单全收，没有大小上限。这三项在作者自己的基线里同样记为 FAIL，两个环境判得一致。

What this run does not show · 这次没跑到的

The fast path is 4 of the bench's ~10 groups. The full run — the 1,086-case unit suite, the third-party interop group (which needs an independent parser installed), the performance thresholds and the 12-condition environment matrix — has not been run in this environment yet. The bench's "three readers, same verdicts" claim rests, so far, on its authors' own runs; this page is the first run by a different operator, and it covers the bench, not yet the three-reader claim.

快跑是台子约 10 组里的 4 组。全量跑（1086 例单测、需要第三方解析器的互操作组、性能阈值、12 项环境矩阵）还没在这个环境跑过。台子「三读者同判」的说法目前只有作者自跑记录；本页是第一个异机运行，它覆盖的是台子本身，还没覆盖三读者那条。
