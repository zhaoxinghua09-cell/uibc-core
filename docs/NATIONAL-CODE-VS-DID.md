# 国标身份码 ≠ `did:cn`：两套标识，别混着说

2026-11-24。**目的：防止把"信通院平台给的 DID"对外说成"国标身份码"。**

## 一、两套东西，各自的出处

| | 国标身份码 | `did:cn` |
|---|---|---|
| 依据 | **GB/Z 185.2—2026**《人工智能 智能体互联 第2部分：身份码》，2026-05-22 发布，现行；归口 SAC/TC 28 | W3C DID Extensions 注册表里的 `did:cn` 方法；规范只有一份 README（6,536 字节） |
| 结构 | **分层 OID 标识**（遵循 GB/T 26231）：`身份码OID.版本.身份注册服务方.身份注册请求方.自定义序列号`，数字/字母、以 `.` 分隔 | `did:cn:<issuer>.<industry>.<enterprise>`，如 `did:cn:88.100.1` |
| 谁分配 | **身份注册服务方**统一分配；一码一智能体 | 标识由持有者按方法规则生成，注册中心只做注册与解析 |
| 性质 | **国家标准化指导性技术文件**（GB/Z，不是强制 GB/T） | 事实标准（W3C 注册的方法） |
| 起草单位 | 北邮、中国电子技术标准化研究院、华为、蚂蚁、阿里云等 31 家（该页名单中**未见中国信通院**） | 运营方登记为 CAICT / Astron |

**结论：这是两条标准化路线。** GB/Z 185 系列由电子标准院（TC28）主导、走 OID；信通院智能体标识与身份网络走 **"区块链 + DID + 超级智能体"**，签约时给的是 **基于 VC 的智能体身份标识，并与原有 DID 关联使用**。两者可以并存，但不是同一个码。

## 二、所以"给我们的 agent 映射国标身份码"能做到哪一步

| 步骤 | 现在能不能做 | 缺什么 |
|---|---|---|
| 让 agent 拿到 `did:cn` | **不能（写入侧）** | 需要注册方账号与可信互联中心的注册/核验流程；我们只做过只读探测，从未注册 |
| 让 agent 拿到国标身份码 | **不能** | 必须由**身份注册服务方**分配；我们没有服务方资格，也没有 OID 段 |
| 建立 `身份码 ↔ DID` 映射表 | **能，但只能先做"空表 + 规则"** | 需要一段真实分配的码才能验证规则；现在只有标准摘录，没买到全文（16 页，36 元） |
| 解析/校验身份码格式 | **能做，且已可纳入适配器** | 需要标准全文以确认每一段字符集与长度；只用摘要实现容易做错 |

**一句话**：现在能给的是**映射机制**（adapter + 规则 + 双向一致性检查），**不能**给的是**一个真的国标身份码**——那需要分配方的资格与码段，属于组织动作，不是代码动作。

## 三、如果要做，正确的顺序

1. 买标准全文（GB/Z 185.2—2026，16 页）→ 把编码规则逐段写成 ABNF，**不要凭摘要写解析器**。
2. 在 `identity_adapter` 里加第三个适配器（`oid` 型）：只做格式校验与规范化，状态最高给 `INCONCLUSIVE`（格式对不代表这个码被某服务方分配过）。
3. 找一家**身份注册服务方**要一个测试码段（这才是要问对方的事，且不该问信通院——他们的路线是 DID+VC）。
4. 有了真实码段后，做双向映射表并加测试（同一智能体的 `did:cn` 与身份码必须指向同一控制者）。

## 四、对外口径（三条能说 / 三条不能说）

**能说**
- "我们接入了信通院智能体标识与身份网络的**读取侧**：解析 77 个已注册智能体、取到能力与服务端点。"
- "我们的判定层可以消费 `did:cn` 标识，并把平台返回映射进七态。"
- "我们按 T/ISC 0174—2026（智能体网关能力要求，2026-10-28 发布、11-28 实施）做过 43 条一致性对照。"

**不能说**
- "我们已对接成功"——写入侧一条没跑。
- "我们拿到了国标身份码"——那是另一条路线，需服务方分配。
- "平台已验签"——`vcVerificationStatus` 恒为 `SKIPPED`。
