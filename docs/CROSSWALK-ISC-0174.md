# T/ISC 0174—2026 网关能力对照表（uibc-core A2A 网关适配器）

标准：T/ISC 0174—2026《智能体互联网 网联 智能体网关能力要求》（中国互联网协会，2026-10-30 发布）
原文：https://www.isc.org.cn/profile/2026/10/30/1e2b29f9-8aab-438a-9114-e8eadc5f04cd.pdf

## 1. 这份文件是什么，不是什么

**是**：把 0174 的 43 条要求逐条落到本仓库的代码、测试和探针上，并写明每一条的缺口。
**是**：一份可以被外人一条命令复跑的对照——判定不是写死的，探针失败会自动把该条降级为 MISSING。
**不是**：能力评估结论。0174 的评估主体是网关供给方/需求方依据本标准开展的能力评估，我们只是先把自己这半边查清。
**不是**：合规声明。PASS 是我方自证的“行为存在且有可复跑证据”，不等于第三方已认定合格。

判定口径（三条，写下来是为了避免以后自我松绑）：

- `PASS`：条款要求的行为存在，且有可复跑的证据（测试或探针）。
- `PARTIAL`：部分存在，缺口在表里写明。**不四舍五入成 PASS。**
- `MISSING`：本网关不做这件事。**不写成“规划中”。**

## 4. 本轮按 0174 补的四块能力

### 4.1 注册元数据与校验（6.1.1 a/b）

- 代码：`adapters/a2a/registry.py`（`validate_agent` / `validate` / `binding_report`）
- 字段：名称、唯一标识、能力描述、支持协议、通信端点、所属组织，全部必填校验（R1–R7）
- 校验机制：非法标识、非 http(s) 端点、内嵌凭据的端点、重名、重标识一律拒绝（R2/R4/R8）；未知状态码拒绝（R9，对应 6.1.3 a）
- 绑定（6.1.1 b “宜”）：B1 组织标识存在、B2 did:web 主机名与端点主机名一致、B4 凭据签发者为 DID、B5 凭据状态 active、B6 凭据未过期、B7 授权范围存在
- **未知不记通过**：缺凭据时 B3 返回 `ok: null`（不可核验），不返回 True。这是这份表最容易松的一处，刻意钉住。
- 测试：`tests/test_gateway_registry.py`（18 条，含 5 条绑定用例）

### 4.2 身份生命周期闸门（6.1.3 a/b）

- 代码：`adapters/a2a/state.py`
- 闭环：注册 → 启用 → 停用 → 注销，注销为终态，非法跃迁直接报错
- **停用即阻断**：适配器在**每次** `uibc/*` 调用前查状态，停用后下一次调用直接 HTTP 403（`code -32001`，data 里带 `state` 与 `clause: 6.1.3b`），不是“从列表里消失”
- **恢复要重校验**：`resume()` 重跑 B1–B7，任一不是肯定即拒绝并留在停用态，绝不做“翻个开关就恢复”
- 状态可落盘，重启后停用仍然生效（`--lifecycle-state`）
- 测试：`tests/test_gateway_lifecycle.py`（21 条，含持久化与 HTTP 403 实测）

### 4.3 扩展头与追踪连续性（7.3.1 d、9.1.2 a/d）

- 最小公共字段：`X-AUIB-Trace-Id`、`X-AUIB-Source`、`X-AUIB-Target`、`X-AUIB-Protocol-Version`、`X-AUIB-Timestamp`
- 上游带 `X-AUIB-Trace-Id` 时**继承而不覆盖**（多网关链路仍是一条链），缺失时才生成 32 位随机标识，响应头与 body 都回传
- 每次转发写一条访问记录（trace/agent/package/result），对应 9.1.1 a

### 4.4 统一检索与统一记录（6.2.1、6.2.2 a、7.2.1 b）

- `GET /agents?q=&limit=`：字段加权关键词检索，**排序依据、每条得分、命中字段全部回传**（8.1.2 b 要的可解释性，先做到能打印的程度）
- 只返回 `enabled` 的智能体（6.2.2 a）；`limit` 上限 100（6.2.2 b 的限流只做到这一层）
- `GET /agent-record.json`：把 Agent Card 与注册元数据合成一个 `uibc-agent-record/1` 记录，供跨协议统一检索兜底

**能在仓库里补的（我方可独立完成）**

| 条款 | 缺什么 | 补法 |
| --- | --- | --- |
| 6.1.1 c) | 元数据在线编辑与审核 | 加 `gateway/registry/update` 方法 + 审核留痕；先做“变更即重新校验并记录差异” |
| 6.1.1 d) | 行业/场景元数据模板 | 出一套模板 JSON（医械、政务各一），模板即字段子集 |
| 7.2.2 a)-b)、e) | JSON/XML 异构转换与语义一致校验 | 引入零依赖 XML 解析（`xml.etree`），转换后做往返比对，不一致即拒绝转发 |

## 6. 三个必须承认的 PARTIAL（谈判时最可能被追）

1. **6.2.1 a) “语义查询”**：我们是关键词加权，不是语义嵌入检索。叫它“语义”会当场被拆。
2. **9.2.1 a) “权限校验”**：`authorization.scopes` 只被检查“存在”，没有按 scope 拒绝越权调用。这是声明式权限，不是执行式。
3. **9.1.4 “TLS/双向认证”**：适配器自身不做，靠部署层。写在材料里必须写“部署侧提供”，不能写成网关内建。

## 7. 与相邻标准/草案的关系

- **T/ISC 0175—2026**（OpenClaw 类多智能体协同能力要求）：同样要求身份接入、注册、生命周期与访问控制，与本表的 6.1/9.2 高度重合，可作为第二份对照。
- **IETF draft-miao-agw-core-functional-architecture-00**：把网关拆成 A2A / MCP / Model Routing / Network 四类，与 0174 的四域互为映射。做“国内团标 ↔ IETF 草案 ↔ 本实现”三方对照，是别人还没做的事（见项目清单 P2 项）。

## 8. 对外表述的边界（给对接沟通用）

可以用的话：

> 我们按 T/ISC 0174 的四个能力域做了逐条自证，43 条里 11 条通过、19 条部分、13 条缺失，缺失项和补法都在表里；自证脚本一条命令可复跑，探针 18 条全通过。

不能说的话：

- “已符合 0174”——评估主体不是我们。
- “网关能力完备”——路由寻址域 0 条 PASS。
- “支持语义路由/语义检索”——目前是关键词加权。
