# 锚定绑在什么上：两边的 RFC 3161 令牌对象不同（2026-11-20 实测）

**为什么要写这一页**：上一步把 EATF 的载荷搬进 UIBC 包时，有 5 类故障搬不过去。当时只说"没有对应信封"。这一页把它落到字节级事实：**不是缺解析器，是两边的令牌签的不是同一个对象。**

## 实测（解析他们的 13 个 `.aep`，`asn1crypto` 读 `timestamp.tsr`）

```
13 个包里：令牌可解析 12；解析失败的 1 个正是 bad-timestamp（ValueError）
imprint == hash.sha256 文件里的值：12 / 12（可解析的全部相符）
imprint == sha256(canonical.bin)：10 / 13
  不相符 2 个：tampered-canonical-bin（载荷被改，令牌仍签原始哈希，理应不符）
              missing-canonical-bin（没有载荷）
```

**结论**：他们的第三方时间戳绑定的是**载荷哈希**（payload digest）。不是生命周期链头，不是证据根，不是包的状态摘要。

## 我方 S16 要求的是什么

`docs/CHECKS-REFERENCE.md` 的 S16：*"存在真实的第三方时间戳（RFC 3161），且它覆盖的是**本包的链头**"*。我们的 `evidence/external_anchor.json` 指向 `timestamps/anchored_head.json`，那个 head 由生命周期链 + 证据根 + 索引摘要派生（S8/S9 的 checkpoint head）。

所以把一个完好无损的 EATF 包搬进 UIBC 后：载荷、哈希、签名全部对得上，**S16 仍然会判"令牌没有覆盖本包链头"**。这不是谁的 bug，是两种锚定设计：

| | 他们的令牌覆盖 | 我方令牌覆盖 |
|---|---|---|
| 对象 | 载荷摘要 | 包链头（生命周期+证据根+索引派生） |
| 一个令牌能证明 | 这份载荷在某时刻已存在 | 这个包的**全部状态**在某时刻已存在 |
| 换掉生命周期/索引后令牌是否还有效 | 仍然有效（令牌不管这些） | 失效（head 变了） |
| 代价 | 需额外的绑定机制（他们用签名 + 收据）来补 | 令牌要等包定稿才能申请，包不能增量更新后再锚 |

两者都成立，差别是**一个令牌被用来证明什么**。这条不能拿来说谁更强：他们用签名+收据补了绑定，代价是多一个对象；我们用一个 head 换掉多对象，代价是包定稿后才能锚。

## 因此 5 类为什么搬不过去（逐条落到字节）

| 类别 | 字节级原因 |
|---|---|
| `bad-timestamp` | 他们这个包的令牌连 DER 都解不开（`ValueError`）；搬到我们这边，它会先被"解不开"判掉，而我们要测的是"覆盖对象不对"，两者不是同一个规则 |
| `tampered-overt-receipt` | OVERT 收据的 subject 是他们的载荷/回执对；我方 S17 的收据链 subject 是我方 evidence root 与前驱收据摘要 |
| `bad-signature-classical` / `bad-signature-pqc` | 签名对象是他们的 canonical 字节串；我方 seal 签的是 `identity+manifest+lifecycle` 三元组。重签一次就毁掉了这条向量要携带的故障 |
| `untrusted-issuer` | 转换后的包由我方密钥签，不存在"issuer 不可信"这个状态；要复现只能伪造一个我方不信任的 issuer，那是新造用例，不是搬运 |

## 若要让 8 类全部同批比较，唯一诚实的做法

不是"再写一个解析器"，而是**让同一个 TSA 给两边的 head 各签一次**，或者定义一种"绑定中立"的令牌：subject 是一组 `(格式, 摘要)` 对，外加双方的 head。前者要真实 TSA（我方目前只有 FreeTSA 的可解析令牌），后者是一次格式提案，属于对外议题，不是本轮能自证的。

在此之前，对外只能说：**两边的锚定对象不同，因此收据/时间戳故障不可互搬；可互搬的 3 类（载荷篡改、载荷缺失、元数据篡改）已在同一容器里由两套实现同时判出（3/3）。**
