# 第 5 章补节：在他人公开材料上复核一条可证伪的声明

本节记录一次针对**外部**材料的复核，目的不是证明本实现更好，而是检验一种在
本领域常被当作口号使用的说法能否被一条命令推翻。之所以纳入本章，是因为它回答
"这套材料的可信度从哪里来"——来源之一，是别人写下的声明可以被本机重跑并在
不符合时失败。

## 5.x.1　被检对象

`WEXP-dev/wexp-check` 是一个 Agent 证据判定的对照实现，其 `REPRODUCE.md` 给出
语料与参考实现的确切提交号，并声称对照驱动在两处会停：一是语料与其清单
（manifest）不符时，二是个别用例与期望不符时；并且失败会指向发生分歧的具体
字段，而不是把其余检查一律记为通过。

该声明可由一次编辑检验，不需要理解其语义。

## 5.x.2　方法

取语料 `WEXP-CORE-02-VECTORS-001`，复制一份，只把一个布尔值取反：

```
用例 C01 的 expected.asserted_claim_supported：true → false
```

其余字节不动，包括该语料刻意携带的孤立代理字符。这一点很关键：若重新序列化整份
文档，篡改的范围就不再可归因于那一处编辑，复核也就失去意义。随后以该仓库自带的
`comparison.json` 为基线运行对照驱动：

```bash
python3 tools/wexp_negative_control.py --check /tmp/wexp-check \
    --ref /tmp/wexp-ref --vectors /tmp/wexp-vectors --json
```

## 5.x.3　结果

表 5-7　一次单字段编辑后对照驱动的响应

| 观察项 | 结果 |
|---|---|
| 驱动退出码 | 1（非零） |
| 完整性层：语料摘要与其清单不一致 | 报出 |
| 组件层：失败归因到 `asserted_claim_supported` | 报出 |
| 基线层：与已发布比较结果不一致 | 报出 |
| 三层同现 | 是 |

命令输出的四条 `FAIL` 分属三层，其中组件层一行形如：

```
FAIL WEXP-CORE-02-VECTORS-001 case C01: check_equals_expected,
     ref_equals_expected (components ['asserted_claim_supported'])
```

该行是本节的关键证据：它把失败定位到被改动的那一个字段。一个在首次分歧处停下、
并把其余检查计为通过的驱动，无法产生这种输出。

数据来源：`python3 tools/wexp_negative_control.py --json`，退出码 0 表示声明成立。
脚本在临时目录内完成复制、编辑、运行与清理，不改动上游仓库；本仓库不复制、不分发
其语料。摘要值随编辑方式不同而不同，故此处不写具体哈希。

## 5.x.4　本节不成立的推论

下列结论在本节证据之外，本章不作任何暗示：

- 对方期望值的正确性。本次只把一处期望取反，未讨论该期望本身是否恰当。
- 对方语义与任何外部标准的一致性。这类判断需要逐条读规范，非一次运行可及。
- 任何验证器之间的优劣。本节检验的是**对照驱动的行为**，不是判定能力。
- 独立性。编辑、运行、记录均由同一人、在同一台机器上完成；按对方在 IETF 127
  互操作材料中的口径，同一操作者执行的运行不构成独立复现。

## 5.x.5　与本章其余各表的关系

表 5-1 至表 5-6 的数字全部由仓库脚本生成，读者可用表下命令重跑，属于"自证"性质的
内部测量；表 5-7 不同，它的对象在仓库之外，本仓库只能提供复现脚本，不能保证对方
仓库日后不改变行为。两类证据的可信度来源不同，正文不得混用。
