# LICENSE-DECISION · 许可证定案建议（待批准）

> 问题（实测）：同一生态内三种许可证并存，且其中一处用在**代码**上但选的是**内容许可证**。
> | 仓库/组件 | 现状 | 问题 |
> |---|---|---|
> | `uibc-core` | Apache-2.0 | ✅ 一致 |
> | `lgd-engine` | （见仓库 LICENSE） | 需核对 pyproject |
> | `LGD-Eval` | `LICENSE` = **CC BY 4.0**；`skills/lgd-eval/pyproject.toml` = MIT；README 提 Apache | **三处三种，且 CC BY 不适合软件** |
>
> CC BY 4.0 没有专利授权条款，也不处理"分发二进制/嵌入产品"的情形，用它给评测器代码授权，
> 会让企业法务无法出具意见——这在实际销售中是硬阻塞。

## 一、建议方案（三层，按对象类型分）

| 对象 | 建议许可证 | 理由 |
|---|---|---|
| 代码（库、CLI、评测器、工具、MCP 服务器） | **Apache-2.0** | 含显式专利授权与专利报复条款；企业可接受；与 `uibc-core` 现状一致 |
| 规范文本、白皮书、报告、文档 | **CC BY 4.0** | 便于引用与传播；不涉及专利 |
| 测试向量 / 语料（JSON、收据样本） | **CC0 1.0** 或随代码 Apache-2.0 | 避免"用我的向量也要署名"阻碍独立实现 |

**一句话**：**代码 Apache-2.0 / 文本 CC BY 4.0 / 向量 CC0**。不要用一种许可证覆盖三类对象。

## 二、为什么不是 MIT

MIT 更短更宽松，但**缺少专利授权条款**。本生态的核心卖点是"可被大厂安全采用"，
没有专利条款意味着采用方要自己承担专利风险，法务会退回。Apache-2.0 只多几段文字，但解决这个问题。

## 三、为什么不是 AGPL

当前有 1 个 AGPL 仓。AGPL 会传染到"通过网络提供服务"的场景，与"SaaS 化的 Registry/监控"直接冲突。
建议该仓要么改为 Apache-2.0，要么明确标注为"实验、不进入产品路径"。

## 四、需要改动的清单（每项都是一次单独批准）

| # | 对象 | 动作 | 风险 |
|---|---|---|---|
| 1 | `LGD-Eval/LICENSE` | CC BY 4.0 → Apache-2.0 全文 | 不可逆地改变已发布版本的授权（旧 tag 仍按旧证） |
| 2 | `LGD-Eval/skills/lgd-eval/pyproject.toml` | 统一为 `license = "Apache-2.0"` | 低 |
| 3 | `LGD-Eval/README` 许可证段落 | 与 (1)(2) 对齐 | 低 |
| 4 | 15 个无证仓 | 补 LICENSE 占位（Apache-2.0 或 CC BY） | 中：需逐个判断对象类型 |
| 5 | 1 个 AGPL 仓 | 定案改证或标记实验 | 中：涉及已发布授权 |
| 6 | 4 组重名仓 | 合并/归档时同步授权说明 | 低 |

## 五、执行纪律

1. **不改历史 tag 的授权**：已发布的版本保持原证，新版本启用新证，并在 CHANGELOG 写"从 vX 起"。
2. 变更前先在 GitHub 上留一条 issue（可私有）说明范围与理由，便于日后举证。
3. 涉及第三方 fork 的仓不得改证（作者无权）。
4. 每改一仓，同步更新 `docs/LICENSE-MATRIX.md`（待建，一行一仓：仓名/对象类型/许可证/依据）。

## 六、判定"这个仓改不改"的两问

1. 这个仓里的东西会被**嵌入别人的产品**吗？→ 会：Apache-2.0。
2. 这个仓里的东西主要是**给人读的结论**吗？→ 是：CC BY 4.0。

两个都"是"，就拆成两个目录、两份证；不要在一个仓里混装。
