# 中文导读 · uibc-core

> 这份文件只有一个目的：让第一次打开本仓的中文读者，在五分钟内知道**它是什么、它不承诺什么、它被篡改时到底拦不拦得住**。
> 全仓英文为主，本文是中文补充，不替代 README，也不改变任何对外口径。

---

## 一、一句话

uibc-core 是一个**智能体生命周期证据包**与**复核器**：它把"这个 agent 是谁、做了什么、凭什么被允许做"打成可被别人离线复算的包，并给出三值判定——`PASS` / `FAIL` / `INCONCLUSIVE`。

**`INCONCLUSIVE` 永远不能被洗成 `PASS`。** 这是本仓最硬的一条设计约束。

---

## 二、PASS 到底等于什么（原句照抄，不得改写）

> A uibc PASS means: within the observed evidence boundary, no violation was detected. It does not claim the agent was correct, safe, or wise; that the recorded inputs were true or complete; or that any real-world outcome followed.

中文：**在观测到的证据边界内，没有检出违规。** 它不宣称 agent 是正确的、安全的或明智的；不宣称记录的输入为真或完整；也不宣称现实世界里发生了什么结果。

这句话看着弱，但它是本仓能被外部信任的首要原因：**别人能核验的只有"有没有检出违规"，核验不了"它是不是个好东西"。**

---

## 三、三律在这份代码里分别落在哪

| 三律 | 本仓对应物 | 位置 |
|---|---|---|
| **有籍**（Registry） | manifest 里的 agent_id / owner / agent_type / version；登记事件写进生命周期链 | `uibc_core/` + `registry/` |
| **有证**（Evidence） | 证据条目的内容哈希 + `evidence_root` + Ed25519 封签（公钥随包走，可 pin） | `uibc_core/signing.py`、`verify.py` |
| **有门禁**（Gates） | **20 组检查**（逐项编号与覆盖见 `docs/EVIDENCE-INDEX.md`） + 组合校验（K1–K8）；任一不过即 FAIL 或 INCONCLUSIVE | `uibc_core/verify.py` |
| **触点即门** | 每一次"改状态/换钥/回滚"都必须被判一次，不存在"默认放行" | 同上 |

## 四、被篡改时到底拦不拦得住（2026-11-22 实跑）

复跑命令（不需要装依赖、不需要账号）：

```bash
python tools/mutation_benchmark.py
```

**本仓构造的 21 类单点篡改** × 三种验证模式（open / pinned / head-pinned），结果（2026-11-22 复跑，与 11-20 逐位一致）：

| 模式 | 含义 | 假接受率 | 未解释接受 |
|---|---|---|---|
| **open** | 陌生人只拿到包，公钥随包走，无预置信任 | **9.5%（2/21）** | **0/0/0** |
| **pinned** | 依赖方另持公钥，验证时 pin 住 | **4.8%（1/21）** | **0/0/0** |
| **head-pinned** | 专治"整包回滚"，需外部单调锚 | **0%（0/1）** | — |

**"未解释接受 = 0"的意思**：两处被 `PASS` 的篡改，都被检查项明确标为"低置信/需人工确认"，**没有一处是悄悄放过的**。

### 被放过的两类，性质完全不同

| 篡改 | open | pinned | 原因 | 怎么解 |
|---|---|---|---|---|
| **M17 换钥重签（keyswap）** | PASS | FAIL | open 模式公钥随包，密码学上无法区分"新钥"与"合法换钥" | 用 pinned，或与登记簿比对 |
| **M20 整包回滚（旧包冒充新包）** | PASS | PASS | 缺"单调性"——包本身自洽，看不出它比某个新包更旧 | 需外部锚（透明日志 / OTS）；**当前 OTS 仍 `PendingAttestation`，此格尚未覆盖** |

> 换句话说：**这 9.5% 不是漏洞清单，是定义域边界。** 我们主动把它写出来，因为它比"我们全都拦住了"更可信。

### 这个数字值多少：β 与第二套算子（2026-11-22 补跑）

只说一个假接受率是不够的：全拒的验证器也有 0%，因此必须同时给出**假拒绝率 β**；而且，用"修过它的语料"打出来的 0，只能说明这批算子用完了（arXiv 2609.27871 第 10 节把这一点写成了显式批评）。两条都补上：

```bash
python tools/mutation_controls.py
```

| 语料 | 内容 | 结果（open / pinned / head-pinned） | Wilson 95% 上界 |
|---|---|---|---|
| **保持型（算 β）** | 10 个只改表示、不改被签对象的变异（重缩进、键排序、ASCII 转义、CRLF、整包换目录） | 假拒绝 **0/10 / 0/10** | **≤27.8%** |
| **第二套算子（算 α）** | 11 个保留形态、专攻解析与跨文件算术的变异（重复键、BOM、超界整数、索引重复条目、事件重复、链指针前指、值清空、大小写换名、字符数≠字节数） | 假接受 **0/11**（三模式同） | **≤25.9%** |

三点必须一起读：

1. **0 不等于 0**：0/10 与 0/11 的 Wilson 95% 上界分别是 27.8% 与 25.9%，样本小，只能作下界用。
2. **三个变异被裁决出局**：包根加一个未被索引的注释文件（规格未定，不记入 β）、给证据文件加空行（确实改了被摘要覆盖的字节，拒绝是对的——当初标错）、manifest 末尾追加空白（不改变任何被解析或被覆盖的值，改标为良性编辑）。裁决理由写进 `tools/out/mutation_controls.json` 的 `ambiguous_excluded`。
3. **本工具不修任何东西**：先修后测会重造"自己给自己打分"的循环。凡被放过，就记成放过。

## 五、复核一次要多久（2026-11-20 实测，同一条命令两台机器）

命令只有一个：

```bash
python tools/latency_probe.py
```

| 机器 | 干净包 `base`（n=50） | 篡改包 `m_M12`（n=10） |
|---|---|---|
| Windows / Python 3.13（2026-11-19） | median **19.74 ms** · p95 **26.64 ms** · max **38.75 ms** | median 18.42 ms，判定 `FAIL` |
| Linux / Python 3.12（2026-11-20） | median **7.67 ms** · p95 **7.85 ms** · max **8.44 ms** | median 7.71 ms，判定 `FAIL` |
| Linux / Python 3.12（2026-11-21，公网干净克隆复跑） | median **7.78 ms** · p95 **8.69 ms** · max **10.02 ms** | median 7.72 ms，判定 `FAIL` |
| Linux / Python 3.12（2026-11-22 晚，公网干净克隆 + 装 extras） | median **31.71 ms** · p95 **35.82 ms** · max **36.91 ms** | median 30.66 ms，判定 `FAIL` |

**两点必须说清**：

1. **延迟是机器相关的量，跨机、跨依赖状态都不能横向比。** 同一台机、同一条命令，早间裸环境量到 7.20–7.39 ms，晚间装了 `.[verify,interop]` 的干净克隆量到 31.71 ms——**相差 4 倍多**，两次都是真跑，差别来自依赖与运行状态，不是挑数。 上面三行是同一条命令在机器上的输出，不是产品规格；同一版本在不同硬件/系统上相差可达 3 倍（本仓两机即 7.78 ms 对 19.74 ms），**把两个数字并排比大小没有意义**。你机器上跑出来的那个数才算数——所以我们不写单一分位数当卖点，也不写"p99 33.6ms"这种只能复现一次的句子。
2. **单位是整包复核**（全部证据文件哈希 + 生命周期链校验 + Ed25519 验签 + 索引一致性），不是"单次调用判定"。**不要**拿它和策略引擎的亚毫秒指标直接对比——那不是同一个操作。

观察到一个反直觉现象：**篡改包比干净包更快**，因为第一处不一致就返回，不跑完全部检查。这不是性能优化，是逻辑决定的。

## 六、五分钟自证（陌生人视角）

```bash
git clone --depth 1 --branch main https://github.com/zhaoxinghua09-cell/uibc-core.git
cd uibc-core && python tools/external_node_check.py
```

只有同时满足两件事才会打印 `CONSISTENT`：另一个独立编写的复核器与参考实现结论一致，**且**三个必须被拒的包（无时区时间戳、`1900-02-29`、大写 UUID）确实被拒。

### 拿到公开合规包之后：先验字节，再跑用例

下载（或直接读仓内）`conformance/` 之后，**先证明你拿到的字节就是我们发布的那一份**，再谈结论。三条命令，都不联网、不要账号：

```bash
python tools/check_vector_package.py     # ① 逐文件比对 MANIFEST.sha256 ② 核对 0.5.2 压缩包的 pin ③ 覆盖表自检 ④ 跑完 58 例
sha256sum -c conformance/MANIFEST.sha256  # 只用系统自带工具也能复核（清单就是 sha256sum 格式）
python tools/conformance_coverage.py --print  # 每个检查项由哪些用例覆盖；哪几项没有用例、为什么
```

三条各自回答一个问题，缺一不可——注意第一条回答的是“字节有没有被改”，不是“用例设得对不对”，更不是“判定结论必真”：

| 命令 | 它回答的问题 | 它不能回答的 |
|---|---|---|
| `check_vector_package.py` | 这份下载有没有被改过、包和用例还对不对得上 | 用例本身设得对不对 |
| `sha256sum -c` | 同上，但不依赖本仓任何 Python 代码 | 压缩包 pin（清单只覆盖解包后的文件） |
| `conformance_coverage.py --print` | **哪些检查项根本没有用例**（当前 19 项里 16 项有、3 项没有，理由逐个写在 `coverage.json`） | 有用例的那 16 项是否覆盖得充分 |

> 公开覆盖矩阵的意义在于**把空白单元也印出来**：只列"我们测了什么"，读者会默认其余都已覆盖。S9（钉链头）、S16（RFC 3161 外部时间戳）、S19（跨包新鲜度）三项**没有直接用例**（不是"已被覆盖"），只能经替代路径间接触及：head-pinned 模式的篡改基准 M20、`tools/anchor_tsa.py --verify`、红队 RT16。替代路径是攻击测试或独立工具，**不是向量**，因此这三项在覆盖上一律记为空白，写进 `coverage.json` 的 `reason` 字段，不在正文里含糊带过。

## 七、本仓现在还差什么（照实写）

1. **外部复核节点 = 2，且未做利益隔离核验**：以 `docs/EXTERNAL-NODES.md` 为唯一真源——node 001（Debian 13，无特权，按 README 逐字跑）、node 002（macOS，返回 `external_node_result.json`，同一 commit 下与我们判读一致）。两位都是**执行**上的第三方；我们没有对这两方的利益关系做过核验，因此**不称其为利益独立的第三方**，样本量为 2，也不构成统计意义上的独立复现。
2. **公开覆盖矩阵有 3 个空白单元**：19 项检查里 16 项有对应用例，S9（钉链头）、S16（RFC 3161 时间戳）、S19（跨包新鲜度）**没有直接用例**——不是忘了，而是自包含的包无法表达；它们只能经 head-pinned 基准 M20、`anchor_tsa.py`、红队 RT16 间接触及，这些替代路径不计为向量覆盖，理由写在 `conformance/coverage.json` 的 `reason` 字段。
3. **OTS 外部锚 `PendingAttestation`**：所以 M20 那一格还不能宣称已覆盖。
4. **`gate()` 单次判定尚未单独基准化**：上面只有整包复核的分位数。
5. **版本真源曾出现双仓不一致**：本文件所属版本请以本仓 `CHANGELOG.md` 顶端为准。
6. **红队有一处灰区**：16 例攻击里 13 例被拒、**1 例灰区**、2 例按定义放行。灰区是 **RT05（删掉 `seal.json`）判定 `INCONCLUSIVE` 而不是 `FAIL`**——该拦未拦到底，属待收紧项；放行的两例是 **RT08（50MB 证据文件，41 ms 内通过）** 与 **RT10（攻击者自洽重签换钥）**，后者的公钥随包，密码学上无法与"合法换钥"区分，属定义域边界。我们只报 13/16 而不写这三例的性质，就是在藏缺口。
7. **"全量绿"是有前置条件的话**：全量套件需要 `.[verify,interop]`（`cryptography`）。裸 venv 里会成片失败（缺 `cryptography`），Windows 与 Linux 上跑出的用例数也不一样。"零依赖"（单文件 pyz 路径）与"全量绿"（装 extras 后跑测试）是两件事，不能合成一句；具体数字以仓内 `STATUS.md` 为准，我们不在导读里钉死。
8. **克隆命令曾指向不存在的分支**：旧版 README 与本文写 `--branch release/v1.1-precheck`，该分支**在本仓并不存在**，外人照着敲会直接失败。已改为 `main`，并用公网干净克隆实测跑通 `CONSISTENT`——这类错误的性质是"引用正确、命令错误"，比引用 404 更隐蔽。
